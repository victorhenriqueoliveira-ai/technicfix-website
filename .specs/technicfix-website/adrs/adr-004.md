# ADR-004: Autenticação do Admin — Auth.js v5 (NextAuth)

## Status

Aceito

## Data

2026-07-01

## Contexto

O painel admin requer autenticação com e-mail e senha para proteger todas as rotas `/admin/*`. A solução precisa integrar nativamente com o Next.js App Router (middleware de rota, Server Components, Server Actions) e não criar dependência de serviço externo de autenticação.

## Decisão

Usar **Auth.js v5** (NextAuth v5) com o provider `Credentials` (e-mail + senha com bcrypt). A sessão será gerenciada via JWT armazenado em cookie HttpOnly. O middleware do Next.js protegerá todas as rotas `/admin/*` verificando a sessão antes de renderizar.

## Alternativas Consideradas

### Alternativa 1: Lucia Auth

- **Descrição**: Biblioteca leve de auth sem dependência de OAuth, sessões gerenciadas no banco
- **Prós**: Controle total sobre sessões, zero opinião sobre providers, muito leve
- **Contras**: Mais código manual; precisa implementar toda a lógica de criação/invalidação de sessão; manutenção recente descontinuada em favor de abordagem "learn from source"
- **Por que rejeitada**: Auth.js v5 tem integração nativa com Next.js App Router e é mais mantido

### Alternativa 2: Clerk

- **Descrição**: SaaS completo de auth com UI pronta e SDK para Next.js
- **Prós**: Setup em 10 minutos, UI de login pronta, gerenciamento de usuários na dashboard Clerk
- **Contras**: Dependência crítica de serviço externo; free tier limitado a 10.000 MAU; dados de autenticação fora do controle do projeto
- **Por que rejeitada**: Para um único usuário admin com e-mail/senha, o overhead de Clerk não se justifica

## Consequências

### Positivas

- Integração nativa com middleware do Next.js para proteção de rotas sem boilerplate
- JWT em cookie HttpOnly: seguro contra XSS, sem estado no servidor
- Um único usuário admin no MVP: sem necessidade de tabela de usuários complexa inicialmente

### Negativas

- Auth.js v5 ainda em desenvolvimento ativo; algumas APIs mudaram vs v4
- Credentials provider não suporta refresh token automático — sessão expira após `maxAge` configurado

### Riscos

- Hash de senha com bcrypt é síncrono e bloqueante; usar `bcryptjs` async ou `argon2` para evitar bloqueio do event loop em serverless
- Seed do usuário admin inicial precisa ser feito via script (`prisma/seed.ts`) antes do primeiro deploy

## Notas de Implementação

- Configurar `AUTH_SECRET` como variável de ambiente no Vercel (gerado via `npx auth secret`)
- Middleware em `middleware.ts` na raiz: matcher para `/admin/:path*`
- Seed inicial: `npx prisma db seed` cria o usuário admin com e-mail e senha em hash
- Sessão JWT com `maxAge: 8 * 60 * 60` (8 horas) para segurança operacional
